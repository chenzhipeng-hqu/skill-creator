# 嵌入式 Unity 单元测试

在主机 PC 上使用 Unity 编译真实的嵌入式 C 模块，只替换确实需要隔离的依赖。
主机测试用于验证软件行为，不能证明 ARM 构建、固件烧录或真实硬件验证成功。
以少量测试验证核心流程、对外接口和关键异常恢复，不追求函数、分支或状态转换的
穷举覆盖，也不因为代码发生修改就必须新增测试。

## 选择最小化集成方式

1. 创建文件前，先检查仓库的测试说明、现有测试/构建入口、Unity 版本和可复用的
   mock。遵循现有的 Makefile、CMake 或 Ceedling 约定；不要仅因选用了本 skill
   就替换项目正在使用的测试框架。
2. 阅读目标模块及其依赖接口，明确要验证的行为，以及需要隔离的硬件或组件边界。
   编译真实的模块源文件；纯逻辑依赖可以继续使用真实实现。
3. 如果已有测试设施，只添加所需的测试和 mock。如果没有，则在 `tests/` 下创建
   最小可运行的主机测试：一个真实模块、一个测试可执行文件，以及必要依赖。若
   项目没有适用的构建约定，可使用小型 Makefile。

全新独立测试设施可采用以下结构：

```text
tests/
├── unity/          # unity.c, unity.h, unity_internals.h, upstream license
├── mock/           # only needed substitutes; omit if unused
├── src/            # test_<module>.c
└── Makefile        # or the project's established build entrypoint
```

如果项目已有 Unity 依赖，应优先复用。否则从上游项目 `ThrowTheSwitch/Unity` 获取
固定版本或 commit，并在测试设施中记录来源和版本。保留其许可证；不要自行编造
Unity 替代实现。如果缺少源码或必要的主机工具，应如实报告阻碍，不要声称测试
已经运行。

## 确保 mock 忠实于实际接口

- 优先复用真实的公共接口声明，并为其提供替代实现。当绑定硬件的头文件无法在主机
  上编译时，只提供最少的替代声明，并核对其函数签名、类型和常量与生产 API 一致。
  不要手工复制整个组件接口。
- 引号形式的 include 会先搜索源文件所在目录，再搜索 `-I` 路径。仅添加 `-Imock`
  不一定能替换与源文件同目录的生产头文件。必要时通过编译器预处理或 include
  跟踪确认实际解析到的头文件；提出生产代码改动前，先检查是否已有抽象边界可用。
- 不要自动引入 `TEST_BUILD`。确实需要测试专用条件编译时，应将其限制在平台集成
  层；绝不能为了让测试通过而跳过或替换正在验证的生产行为。
- 根据断言需要，为 mock 提供可控输入及可观察的输出、返回值或调用记录。对于测试
  所依赖的行为，不要让 mock 静默返回成功；意外操作应能明确暴露为失败。
- 每个测试前重置可变的 mock 状态，通常放在 `setUp()` 中，例如 GPIO 状态、tick
  计数、回调次数、注入错误和调用记录。按需初始化模块，并在 `tearDown()` 中释放
  每个测试独有的资源。
- 绝不能把 MCU 端口原始地址直接当作数组下标。将支持的端口值映射到有界 mock
  存储，并拒绝不支持的值。
- 通过显式推进模拟时钟来测试时间行为，不要使用休眠。保留真实 tick 的位宽和算术
  规则，以便测试相关超时和回绕行为。回调签名和生命周期必须符合真实 API。

## 按业务场景选择测试

优先覆盖用户要求的一条完整正常流程，再根据实际风险补充重要的失败或恢复流程。
一个用例验证一个有意义的业务场景，不为流程中的每一步单独建立测试。已有用例能
验证本次改动时，复用或扩展，不重复添加；不设测试数量或覆盖率配额。

新增用例前明确：哪项对外行为或关键安全约束可能出错，现有测试为什么不能验证？
新增用例应对应明确的接口约定、风险或真实回归缺陷，不机械展开所有输入组合。
按模块职责选择深度：算法关注计算结果，协议关注编码与解析契约，安全控制关注
必要的中间约束；保留代表性输入和关键边界，不能因精简测试而遗漏这些要求。

通过公开 API 驱动真实模块，只 mock 必要的依赖边界，不 mock 正在验证的行为。
每个测试安排状态、触发真实操作，并用 Unity 断言检查可观察结果；只有注释或
无条件通过的断言不算完成的测试。

优先检查返回值、结果数据、必要副作用、回调和资源释放。仅当调用顺序属于接口
或安全要求时才检查顺序。不锁定无关文案、空格、私有变量或内部实现结构；协议
规定的字节和字段仍需准确验证。

### 状态机：验证完整流程和恢复

通过公开 API、事件和模拟时间驱动真实状态机，不直接修改内部状态来拼装场景。
优先验证正常闭环能完成，结果和通知正确；按风险补充关键异常后的安全状态和
后续任务恢复。有明确约定时，再验证重复启动、取消或迟到事件等受限操作。

不逐个断言内部中间状态，也不逐条枚举状态转换；只有状态对外可见且被调用方
依赖，或涉及安全约束时才检查。例如必须先关闭输出再通知完成，就应验证这个
顺序，不能仅检查最终输出已关闭。

异常与恢复尽量放在同一个用例中，确认模块能继续接受并完成后续任务；除非恢复
契约明确要求，否则不要在两者之间重新初始化模块或清空 mock，以免掩盖恢复缺陷。
各独立用例之间仍按 `setUp()` 规则重置。超时使用模拟时间；阈值属于关键契约时，
再检查阈值前后的行为。

## 构建与运行

使用原生主机 C 编译器和适当的警告选项进行构建。链接真实模块、选定的真实依赖、
必要的 mock 实现、Unity 和测试运行器；不要同时链接已被 mock 的符号对应的硬件
实现。确保源文件和头文件的修改会通过现有构建系统或编译器生成的依赖文件触发
重新构建。不要要求所有主机平台都使用 `.exe` 后缀。

遵循 Unity 的 runner 约定（`UNITY_BEGIN()`、`RUN_TEST(...)`，并在 `main()` 中
返回 `UNITY_END()`），或使用项目已有的生成式 runner。构建/测试入口必须在编译
失败或断言失败时返回非零退出状态。

## 验证并交付结果

1. 通过构建入口运行目标测试；对于默认 Makefile 结构，从仓库根目录运行
   `make -C tests test_<module>`。
2. 对新建的测试设施，临时让一个有意义的断言失败，并确认同一入口返回非零状态。
   然后恢复断言并重新运行成功；最终文件中不得保留故意失败的断言。
3. 如果已有相关测试套件，运行它以发现集成问题或共享 mock 回归。明确报告跳过或
   受阻的检查。
4. 报告修改的文件、准确命令、测试数量与结果，以及限制。将主机/mock 测试证据与
   ARM 编译和真实硬件验证分开说明；本工作流程不授权烧录或控制硬件。
